# Study Derivability — Consolidated Findings

## Core Thesis

**The Derivability Hypothesis**: A ground-truth CBMC assertion's probability of being
generated by an LLM is determined primarily by how much of it is textually derivable
from the function body alone. Two distinct barriers limit generation:

1. **Knowledge barrier**: Required information is structurally absent from the provided text
2. **Strategy barrier**: Required information is present, but the LLM does not write it
   by default (it requires a generation pattern to be demonstrated)

- s2n-tls: 35 stuffer functions, assertions in harness headers
- FreeRTOS-Plus-TCP: 55 functions with ≥1 ASSERT assertion

## Phase 1 — Ground Truth Dataset

- 1,200 GT assertions extracted (CBMC for aws-c-common, regex for s2n/FreeRTOS)
- Taxonomy join rate: 95.8% (183/191 taxonomy rows matched to gt_assertions.csv)
- FreeRTOS key finding: assertions are inside **stub function implementations**, not the
  main harness body, requiring knowledge of which helper functions the target calls.

## Phase 2 — Feature Engineering

Ten features computed per assertion (1,200 rows):

**Knowledge barrier indicators:**
- `f_var_overlap` — variable names from function signature appear in assertion
- `f_field_overlap` — struct fields in assertion appear in function impl
- `f_predicate_in_impl` — the named predicate appears in the function body
- `f_predicate_in_postcond` — predicate appears in documented postconditions
- `f_predicate_in_nl` — predicate appears in NL doc (rare: ~3.8% positive)
- `f_uses_cbmc_builtin` — assertion uses __CPROVER_r_ok or similar

**Strategy barrier indicators:**
- `f_is_frame_negative` — assertion checks old_X == current_X (frame condition pattern)
- `f_position_post_call` — assertion appears after the function call (true postcondition)
- `f_negation_depth` — negation depth (complex structure)
- `f_arity` — number of sub-expressions

Sanity checks:
- FRAME_COND detection rate via f_is_frame_negative: 84.4%
- DOMAIN predicate_in_impl detection: 87.9%

## Phase 3 — FreeRTOS LLM Generation (condA and condE)

**Key finding**: FreeRTOS recall is almost entirely driven by textual derivability from
the example harness.

### Module-level recall (E_claude, partial results at 62/220):
| Module | Mean E_claude | N>0 |
|--------|--------------|-----|
| DHCP   | 0.834        | 2/2 |
| DHCPv6 | 0.042        | 1/4 |
| ARP    | 0.000        | 0/2 |
| DNS    | 0.000        | 0/4 |
| IP     | 0.000        | 0/1 |

**Mechanism**: DHCP module functions (DHCPProcess, DHCPProcessEndPoint) share the same
stub implementations. When one is shown as an example (condE), the LLM copies those
stubs verbatim including their `__CPROVER_assert` calls → 100%/67% recall.

Other modules: examples show different stubs → stubs can't be reused → 0% recall.

### Condition A recall (domain knowledge):
- `DHCPv6Process_PassReplyToEndPoint`: A_claude=100% (2/2) — guessed pxEndPoint and
  pxDHCPMessage from function name (domain knowledge, not derivability)
- `DNS_TreatNBNS`: A_qwen=20% (1/5) — guessed pucEthernetBuffer != NULL from common
  FreeRTOS pattern knowledge

### FreeRTOS interpretation:
The assertions are in stubs that implement helper functions called by the target. To know
which helpers to stub and what to assert, the LLM needs the target's call graph — a
**knowledge barrier** since the harness header doesn't reveal this. Condition E only
helps when the example function calls the same helpers.

## Phase 5 — Falsification Probes

### Probe 1: Strategy barrier test — wrong-family example (F) for FRAME_COND
```
FRAME_COND:
  Claude: A=0.00, B=0.19, E=0.50, F=0.50  (Fisher E vs F: OR=1.0, p=1.0)
  Qwen:   A=0.41, B=0.47, E=0.56
```
**Result**: F = E for FRAME_COND — any example teaches the frame condition pattern.
This CONFIRMS the strategy barrier: the pattern (old_X == X) is structural, not
family-specific. No falsification.

### Probe 2: Knowledge barrier test — VALIDITY_PRED under F
```
VALIDITY_PRED:
  Claude: A=0.00, B=0.06, E=0.43, F=0.06
```
**Result**: F barely outperforms B (wrong-family example ≈ no example) for VALIDITY_PRED.
The knowledge (which predicates to check) requires the RIGHT example. No falsification.

### Probe 3: Absolute floor confirmation
```
CBMC_BUILTIN, OVERFLOW_ARITH, ZERO_CHECK: 0% under ALL conditions for both models
```
These require runtime CBMC machinery information (pointer validity, arithmetic overflow
bounds) that is absent from all provided text. No prompting strategy can overcome this.

### Probe 4: Condition progression (FRAME_COND vs VALIDITY_PRED, claude)
```
               A     B     C     D     E     F
FRAME_COND:   0.00  0.19  0.16  0.09  0.50  0.50
VALIDITY_PRED: 0.00  0.06  0.11  0.03  0.43  0.06
```
Both categories show the E jump. FRAME_COND also shows F=E (strategy unlock).
VALIDITY_PRED shows F≈B (knowledge barrier, family-dependent).

## Three-tier structure (main empirical finding)

1. **Absolute floor** (knowledge barrier, absolute):
   CBMC_BUILTIN, OVERFLOW_ARITH, ZERO_CHECK, TYPE_VARIANT (mostly)
   — 0% under all conditions, both models
   — Information is absent from all provided text

2. **Strategy-resolvable** (strategy barrier):
   FRAME_COND (50% under E or F), RETVAL_SPEC (20% under E or F)
   — Any example with the pattern unlocks these
   — Qwen already has the strategy internalized (41% under A)
   — Claude requires demonstration

3. **Family-context-dependent** (knowledge barrier, partially derivable):
   VALIDITY_PRED (43% under E, 6% under F)
   STRUCT_PTR (22% under E, 4% under F)
   — Same-family example provides the specific vocabulary (predicate names, field names)
   — Wrong-family example doesn't help
   — Confirmed in FreeRTOS: only same-stub-family functions get high recall under E

## Implications

1. **For tool design**: Automatic example retrieval (condE) from the same module is the
   highest-leverage intervention (roughly 3× improvement over no example for derivable
   categories). Strategy barriers can be overcome with any domain example; knowledge
   barriers require family-matched examples.

2. **For prompt engineering**: Chain-of-thought (C, D) provides minimal gains (2-3pp)
   over code-only prompts (B). The information is either present (and pattern needs
   demonstration) or absent (and no amount of reasoning helps).

3. **For corpus design**: The three-tier structure predicts which assertions are worth
   automating. CBMC_BUILTIN and arithmetic assertions should be generated by rule-based
   tools, not LLMs. FRAME_COND and VALIDITY_PRED are the productive LLM targets.

4. **For FreeRTOS-style proofs**: Stub-based assertions require an oracle about which
   helper functions the target calls. This is a fundamental knowledge barrier that cannot
   be resolved without providing the target's implementation or function call graph.
